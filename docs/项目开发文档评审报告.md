## 1. 结论摘要

- 当前开发文档已经从 PRD 升级为可执行的双人开发基线，具备产品边界、前后端分离、模块依赖、技术选型、数据库方案、双人分工、接口契约、测试门禁和发布回滚规则。
- 文档对生命周期指南中的需求分析、架构设计、开发实现和测试验证覆盖较好。
- 文档对上线部署和后期维护已经有方向，但生产环境证据、监控面板、事故响应和定期巡检仍需要在 M0-M6 形成实际文件和记录。
- 数据库部分已经明确本地 SQLite 与云端 PostgreSQL 的边界，并提供 Mermaid ER 关系；正式开发前仍应把 ER 图落为仓库文件，并输出可执行的 SQLAlchemy Model、Alembic 初始迁移和数据字典。
- **建议状态：有条件通过。** 允许两人做契约、建库和 Stub；在 G1 架构门禁前，不允许开始大规模业务开发；在 G5/G7 之前不得宣称可生产上线。

## 3. 数据库架构评审

### 3.1 设计正确的地方

- 将商户业务数据和云端控制数据分开，符合本地优先和隐私目标。
- 使用 `inventory_event` 作为库存事实来源、`inventory_balance` 作为投影，避免直接覆盖库存导致无法审计。
- 本地业务库包含导入、分析、备份、同步和审计，能够支持客户的完整操作闭环。
- 云端控制库不建立完整 `sku`、`movement`、`unit_cost` 表，降低敏感数据集中化风险。
- 已规定外键、唯一键、检查约束、索引、迁移、备份和恢复验证，方向符合规范。

### 3.2 仍需在建库前确认

- 数量和金额的精度：建议冻结基础单位、数量 scale、金额最小单位、币种和四舍五入规则。
- 库存事件方向：明确入库、出库、退货、报废、盘点、调拨和冲销对余额的正负含义。
- 批次库龄：确认 FIFO、批次快照或无批次商品的降级规则。
- `inventory_balance` 重建：提供从事件重放、快照校验和损坏恢复脚本。
- 单主工作台写入：明确 UI、同步、调度是否通过同一个本地应用服务串行写入。
- 本地数据库是否使用 SQLCipher：如果第一版不做，必须在隐私说明中明确保护边界。
- 云端 `sync_envelope` 的最大大小、过期时间、重试次数和失败事件清理策略。

### 3.3 建库完成证据

- `docs/er-diagram.md`：本地库和云端控制库两张 ER 图。
- `local-data/migrations/versions/0001...` 至 `0007...`：可重复执行的 Alembic 迁移。
- `services/control-plane/migrations/versions/0001...` 至 `0007...`：云端迁移。
- `scripts/verify_schema.py`：表、索引、外键、唯一键和 PRAGMA 检查。
- `scripts/verify_backup_restore.py`：备份、临时恢复、完整性和样例查询。
- `docs/data-dictionary.md`：字段、类型、单位、空值、来源、敏感级别和保留期限。

## 4. 两人分工评审

### 开发者 A 的边界

- 负责官网、Web、控制 API、本地数据库、工作台 UI、托盘 Agent、同步、备份、打包、发布和运维。
- 负责物理数据库和迁移是合理的，因为 A 负责工作台和 API 的事务边界。
- A 不应自行定义 KPI 公式；只能实现标准化适配和结果展示。

### 开发者 B 的边界

- 负责标准化输入契约、引擎、Skill、基准、黄金结果、边界测试和性能测试。
- B 不直接维护 ORM、API 或数据库迁移是合理的，能够保持引擎纯度和可独立发布。
- B 必须对每个需要的字段、单位、空值和参数缺失状态负责，不能只交付公式代码。

### 共同边界

- contracts、OpenAPI、错误码、指标口径、同步事件和发布验收必须共同评审。
- 任何跨边界变更必须同时带 Schema、测试、版本和交接说明。
- 当前分工没有明显职责重叠，但 A 的范围较大，必须严格按 MVP 顺序削减官网视觉、AI 润色和高级报表。

## 5. 技术选型评审

- **通过**：PySide6、SQLite、SQLAlchemy、Alembic、FastAPI、PostgreSQL、Next.js、TypeScript、SSE、PyInstaller、pytest 和 Playwright 与项目规模匹配。
- **通过**：第一版不引入 Redis、消息队列和微服务，符合生命周期指南“简单优先”的建议。
- **需验证**：`uv workspace`、PyInstaller 与 pandas/scipy/statsmodels 的体积和 Windows 打包兼容性必须在 M1/M6 真实构建，不可只凭选型判断。
- **需明确**：托盘进程被用户退出后调度不会执行，文档已经承认该限制；必须在 Web 状态中标记离线和错过任务，不得伪报成功。
- **需修正**：生命周期指南中的 MySQL、Redis、PM2、Nginx 示例只能作为通用参考，本项目应使用 PostgreSQL、Docker Compose、Caddy、SSE 和托盘 Agent 的实际运行手册。
- **需加强**：生产开发者账号必须 MFA；商户密码使用 Argon2id；Refresh Token 需轮换和撤销；日志必须字段白名单脱敏。

## 6. 测试和验收评审

- 测试金字塔已建立，核心引擎黄金数据和属性测试方向正确。
- `FakeEngine` 让 A 可以先完成 UI 和 E2E，是降低并行阻塞的有效设计。
- 需要把测试结果变成可归档证据：数据版本、代码版本、依赖版本、机器配置、命令、输出和失败项必须保存。
- 需要把“误差为 0”“MAPE ≤ 25%”改成具体容差、数据集、样本量和统计口径；生命周期指南要求需求可验证，不能保留模糊验收。
- 需要新增桌面专项测试：托盘、单实例、SQLite 锁、断网、重启、备份恢复、升级迁移和安装卸载。
- 需要新增安全专项测试：商户越权、开发者 Scope、Token 撤销、配置签名、诊断包脱敏和安装包签名。

## 7. 上线和运维评审

### 已覆盖

- 环境分离、`.env.example`、Docker Compose、HTTPS、CI/CD、版本签名、灰度、回滚、备份、恢复和日志方向已经写明。
- 本地业务库与云端控制库的恢复责任不同，文档已经避免把云端控制库丢失等同于商户本地业务丢失。

### 未达到生产门槛

- 没有实际 staging/production 的部署清单、服务器资源、域名、证书、密钥和防火墙记录。
- 没有可执行的 Prometheus/Grafana 或等价监控面板和告警规则。
- 没有完整事故响应手册：发现、分级、止损、回滚、通知、复盘和改进责任人未落到文件。
- 没有日志轮转、技术日志保留、删除任务和磁盘告警的实际配置。
- 没有依赖升级日历、漏洞评分和紧急补丁流程的执行记录。
- 没有商户注销、版本退役、密钥撤销和数据删除证明的实际操作流程。

## 8. 评审后的必须修订清单

按优先级排序：

1. **P0**：将主基线中的本地/云端 ER 关系归档为仓库文件，并完成数据字典、初始迁移和库存事件守恒测试。
2. **P0**：冻结 KPI、COGS、库龄、ABC、补货、预测和误差口径，并为每个口径建立黄金数据。
3. **P0**：完成 contracts、OpenAPI、同步信封和错误码的正反例契约测试。
4. **P0**：完成商户/开发者权限越权测试，验证每个 API 都有后端 Scope 检查。
5. **P1**：将 staging 部署、备份恢复、配置灰度和回滚做成可执行 Runbook。
6. **P1**：接入 CI 覆盖率、依赖扫描、SBOM、安装包签名和产物归档。
7. **P1**：建立监控、告警、日志轮转、事故响应和定期巡检文件。
8. **P1**：建立需求矩阵、用户故事、原型确认和变更记录。
9. **P2**：补充多行业产品配置、官网内容审核和小程序正式接入前的微信合规材料。

## 10. 最终意见

- 这份开发文档**符合软件开发全生命周期的结构和基本规范**，尤其是分层架构、两人协作、契约优先、测试金字塔和版本回滚设计较完整。
- 它当前的不足不是“缺少更多技术名词”，而是部分规范尚未转化为可执行文件和可验证证据。
- 可以从 M0 开始建库、写 contracts、搭 CI 和 FakeEngine；不要跳过 M0 直接进入大规模页面或公式开发。
- 只要按本报告的 P0/P1 清单完成，文档就可以从“开发前基线”升级为“可持续执行的项目工程规范”。

**评审结论：有条件通过，准予进入 M0；生产上线须重新执行 G5/G7 发布评审。**
