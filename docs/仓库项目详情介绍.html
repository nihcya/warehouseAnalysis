仓库品类分析决策工具
项目背景 解决方案 架构与数据 交付与边界

PROJECT OVERVIEW · V1.0

让仓库数据变成每天能执行的决定

仓库品类分析决策工具是一套本地优先的库存分析与调度工作台。它把商户已有的 Excel、CSV 和业务流水，整理成可追溯的动销、库存、库龄、积压和补货信息，并在客户自己的电脑上完成核心处理。

一句话理解：云端负责账号、授权、配置和运行状态；商户的货品、库存、成本、采购和分析明细主要留在本地。

这不是普通的云端库存 SaaS

它更像“本地业务工作台 + 云端控制台”：客户断网时仍能完成核心工作，联网后同步授权、配置、任务状态和必要的脱敏技术信息。

本地优先业务明细留在商户电脑
可追溯数据期间与公式版本可查
可恢复备份、导出和迁移可验证
可扩展未来接入扫码和多行业

一、项目背景：仓库最难的不是记账

很多商户已经有进销存软件、Excel 或收银系统，真正困难的是数据分散、口径不一，最后仍然只能凭经验决定采购和库存处理。

1

数据分散，无法形成统一判断

货品资料、出入库流水、采购价格和盘点结果来自不同文件。字段名称、单位、时间范围不一致，管理者很难快速确认哪一份数据可信。

2

库存看得见，问题排不出来

库存总量并不等于经营健康。真正需要知道的是哪些品类动销快、哪些已经积压、哪些临近缺货，以及问题发生在哪个周期。

3

采购依靠经验，缺少可解释依据

只看历史销量会忽略提前期、安全库存、在途量和季节变化。采购建议如果不能解释来源，客户也不敢真正采用。

4

网络和隐私成为现实阻力

商户不愿把成本、采购价、供应商和完整流水放入第三方云端；仓库现场网络也可能不稳定，不能让核心工作依赖在线状态。

5

结果做出来了，却没有持续执行

一次性分析报告很快过期。没有定时任务、异常提示和运行状态，团队仍然要手工重复整理数据。

6

移动录入方便，直接连本地又不安全

扫码录入适合仓库现场，但微信小程序不能直接访问商户电脑数据库，需要经过受控、可过期、可追踪的同步中继。

客户真正想要的不是更多图表：客户需要的是“数据不会丢、结果看得懂、建议有依据、断网能工作、出问题有人能定位”。

二、我们如何解决：把复杂问题拆成四条主线

第一版先解决稳定、可解释、可恢复的本地闭环，再逐步开放移动采集和更复杂的协同能力。

A

先统一数据，再进行分析

通过导入向导完成字段映射、单位换算、日期校验和重复提示。错误按文件行号、字段和错误码定位，避免用户反复试错。

  • 保留原始导入批次和错误记录
  • 库存事件追加记录，不静默覆盖历史
  • 余额由事件投影，可重建和核对
B

把指标变成可解释的采购依据

核心引擎计算动销、周转、ABC、库龄、呆滞、补货和预测，并在每个结果中保存数据期间、单位、公式版本、输入摘要和警告。

  • 数据不足时明确提示，不伪造精确结论
  • 建议量展示安全库存、提前期和在途量
  • 同一输入和版本得到可重复结果
C

本地完成业务，云端只做控制

商户完整业务库放在本地 SQLite；云端 PostgreSQL 只保存账号、许可证、设备、配置、任务、心跳、脱敏日志和临时加密信封。

  • 断网仍可导入、分析、报告和备份
  • 联网后同步配置、授权和状态
  • 不默认建立云端完整 SKU 和库存明细表
D

让运行过程持续可见、可恢复

托盘 Agent 负责后台心跳、任务、配置和同步。Web 端显示工作台是否在线、任务是否成功和是否有同步积压；升级前自动备份。

  • 配置和版本支持签名、灰度和回滚
  • 失败任务保留错误码和 request_id
  • 诊断包默认脱敏，客户确认后再上传

三、产品由哪些部分组成

各端职责明确，避免把业务数据、管理能力和移动采集混在一起。

官网与下载中心产品介绍、安装包、校验值、版本说明、操作文档、隐私和支持入口。
商户 Web 管理端账号、许可证、设备在线状态、任务状态、小程序绑定和同步积压。
开发者管理模式统一管理商户、产品类型、配置、Skill、版本、日志和技术支持授权。
本地 Windows 工作台导入、库存、分析、调度、报告、备份和恢复，核心业务不依赖网络。
微信小程序预留未来负责扫码入库、出库、盘点和采购录入，本期只做接口、Schema 和 Mock。

四、客户使用流程

从下载安装到日常使用，客户不需要自行安装 Python、数据库或复杂运行环境。

01 · 下载

选择行业安装包

从官网选择零售、批发等产品类型，下载带签名和 SHA-256 校验值的 Windows 安装包。

02 · 登录

注册商户账号

登录工作台，注册设备并获取许可证、产品配置和离线宽限期。

03 · 导入

整理历史数据

导入 Excel/CSV，完成字段映射、错误修复和库存事件校验。

04 · 分析

生成经营结果

在本地执行指标、分类、库龄、补货和预测，生成可导出的报告。

05 · 调度

按计划自动运行

托盘 Agent 在后台执行任务，窗口关闭后仍可运行，并记录成功或失败状态。

06 · 查看

Web 端看运行状态

商户查看设备在线、最后心跳、任务状态、版本和同步积压，不直接暴露完整业务明细。

07 · 采集

未来接入扫码

小程序登录并绑定工作台，提交事件到临时加密中继，不能直接访问本地数据库。

08 · 保护

备份与恢复

升级和重要操作前自动备份；恢复到临时库校验通过后再切换，失败不覆盖当前数据。

五、数据放在哪里

本项目最重要的产品承诺是数据边界清楚。云端能看到运行是否正常，但默认看不到商户完整库存明细。

位置保存内容默认行为客户可感知的价值
商户电脑
SQLite 本地业务库		SKU、条码、仓库、库存事件、成本、采购、批次、分析结果、报告和完整业务审计。本地保存、断网可用；数据库和备份放在用户数据目录，不放安装目录。隐私边界清楚，网络中断时核心工作不中断。
开发者平台
PostgreSQL 控制库		账号、许可证、设备、产品类型、配置、版本、任务、心跳、同步状态和脱敏技术日志。不默认保存完整 SKU、库存数量、成本、采购价格和业务报告。统一授权、版本和技术支持，多端状态可见。
临时中继
加密同步信封		小程序事件的密文、事件编号、目标设备、状态和过期时间。短期保存；工作台确认后删除原始密文，失败只保留状态和错误码。兼顾扫码便利与本地数据边界。

六、前后端如何连接

前后端分离不是把所有数据都搬到云端，而是把职责拆开：

  • Web 前端只通过 FastAPI `/api/v1` 和生成的 OpenAPI Client 访问云端。
  • 工作台 UI 只调用本地 Application Service，不直接拼 SQL、不直接调用 HTTP。
  • 托盘 Agent 负责心跳、配置、任务和同步；核心引擎只接收标准化数据对象。
  • 所有跨端请求带版本、租户、设备、request_id 和幂等键，失败可定位、重复可安全重试。

七、第一版技术与界面方向

第一版优先服务仓库管理者和采购负责人，追求长时间使用时的清晰与稳定，而不是营销式视觉。

桌面工作台

Python 3.11、PySide6、SQLite、SQLAlchemy 2、Alembic、pandas、numpy。

左侧导航、顶部网络/授权/同步状态、中心表格与筛选，导入使用分步向导。

云端控制平面

FastAPI、Pydantic 2、PostgreSQL、Docker Compose、Caddy HTTPS。

通过 SSE 推送状态，30 秒轮询作为断线降级；第一版不预先引入 Redis 和消息队列。

Web 与发布

Next.js、React、TypeScript、Ant Design、TanStack Query、Playwright。

统一官网、商户端和开发者端，后端 Scope 决定权限，界面切换按钮不能代替权限。

UI 设计关键词

  • 仓库运营控制台：克制、清晰、可扫描
  • 深蓝导航、青绿成功、琥珀警告、红色错误
  • 表格、筛选、状态、错误定位优先
  • 不使用大面积渐变、模糊背景或装饰性大卡片

客户能看到的状态

  • 本地可用 / 云端待同步
  • 任务运行中 / 成功 / 失败 / 错过
  • 设备在线 / 降级 / 离线 / 已撤销
  • 配置和版本是否已确认生效

八、第一版交付什么，暂时不做什么

明确范围是为了保证第一版真的能交付，而不是把所有未来设想都变成不稳定的承诺。

第一版交付

  • Windows 可安装工作台，无需客户单独安装 Python 或数据库
  • 本地导入、库存事件、分析、报告、备份、恢复和导出
  • 账号、设备、许可证、配置、任务和运行状态管理
  • 开发者管理模式、版本发布、灰度和诊断支持
  • 小程序接口、Schema、Mock 和同步集成验证
  • 安装、升级、回滚、断网和数据恢复测试记录

第一版明确不做

  • 微信小程序页面开发、审核和正式发布
  • 商户员工邀请和复杂组织权限
  • 多主工作台的实时双向合并
  • 云端完整库存业务库和默认云端业务备份
  • 动态下载并执行任意 Skill 脚本
  • 在缺少真实数据时承诺采购建议一定被采用

九、两位开发者如何保证可以接上

平台与引擎通过公共契约协作，而不是互相引用内部代码。

平台与工作台负责人

负责官网、商户 Web、开发者模式、FastAPI、SQLite、导入、备份、托盘 Agent、同步、打包和发布。

验收重点：客户能安装，数据能导入，分析能展示，状态能同步，升级失败能恢复。

引擎与 Skill 负责人

负责数据标准化、KPI、ABC、库龄、补货、预测、行业基准、Skill、黄金数据和性能评测。

验收重点：相同输入可重复，公式可追溯，异常有 Warning，wheel 可独立安装。

共同规则：接口使用版本化 JSON Schema/OpenAPI；A 先用 FakeEngine 开发页面，B 提供真实 engine wheel；任何字段、单位、公式或状态变化，都必须带 Schema、测试和兼容说明。

十、客户最关心的问题

断网后还能不能使用？

可以。导入、查看本地数据、运行分析、生成报告、备份和导出属于本地能力。账号状态、配置、任务状态和小程序事件同步需要网络，恢复网络后再处理。

开发者能不能看到我的库存和采购价格？

默认不能。云端只保存控制面数据和脱敏技术日志。小程序事件如果必须经过云端，只以短期加密信封中继，工作台确认后按策略删除密文。

如果升级失败，数据会不会丢？

升级前自动备份，迁移在校验通过后切换；失败时进入安全模式并保留当前有效数据库，不通过删除数据库重新初始化来“解决”。

第一版可以直接用微信扫码吗？

第一版只完成接口、Schema、Mock 和同步协议验证，不开发小程序页面和微信发布流程。正式扫码能力会在协议稳定、隐私和微信合规材料完成后开放。

分析结果是不是一定正确？

结果会记录数据期间、公式版本、引擎版本、输入摘要和警告。指标必须通过黄金数据和边界测试；数据不足或口径未确认时会明确提示，不把不确定性隐藏掉。

十一、项目当前阶段

项目已完成开发前架构梳理，正在进入 M0 冻结阶段。正式编码前需要共同确认：

  • 公共 contracts、OpenAPI、错误码、单位和金额精度。
  • 本地/云端 ER 图文件、Alembic 初始迁移、数据字典和备份策略。
  • 核心指标公式、黄金数据、UI 线框和环境启动脚本。
  • 隐私边界、同步信封 TTL、配置签名、离线宽限期和回滚方案。

生产发布条件：安装、升级、恢复、安全扫描、试点反馈、监控告警和发布审批全部归档后，才进入正式发布。
